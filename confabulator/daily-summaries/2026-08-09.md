## Why my number was wrong, and it is a live problem

`kw_daily` last updated **2026-08-05 20:39**. Its only writer is `scripts/ingest-keyword-csv.mjs`, a
manual CSV import. There is no automated per-keyword daily history in this repo. `word-spend.mjs`
reads it, and `ad-engine.ts:761` reads it as the engine's *preferred* evidence source, falling back
to an average when rows are missing. It ages out silently and nothing alerts on it.

`ads-month.mjs` is also broken: hardcoded June dates, so it 400s on a 68-day range.

## Rule 1 — the $0.85 ceiling is account-wide now

William: *"after .85 we communicate to confirm you dont go over $.85 per keyword."*

The ceiling existed but bound only the ladder, the path for words that will not spend. The ROAS bid
search ran to `BID_CAP` at $2.50 instead, with a comment in the code stating the $0.85 stop was
gone. That is exactly how one word compounded to $1.94.

Both paths stop at the same number now. A bid climbs onto $0.85 and stops. Crossing it is never
automatic, it is reported and waits. Cuts are untouched, because lowering a bid needs no permission.

Live dry run: 71 bid changes, highest $0.85, none above it. Two keywords wanted more and were left
alone and named instead.

## Rule 2 — in-month revival once attribution credits the sale

William: *"if a word is turned off and the 14 day attribution kicks in for sales dont turn it back
on that month until that word reaches a 2.0 roas"*, then *"turn it back on the moment the attribtion
credits it above a 2.0."*

Before this, the only way back was the monthly reset on the 1st, so a word vindicated on the 3rd sat
dark for four weeks. The engine now re-checks its own kills every six hours, on the same
month-to-date rows the kill already reads, and re-enables at 2.0x.

Scope is deliberately narrow: only words **this engine** killed, **this month**, and only while
**still paused**, so a manual re-enable is never written over.

**It cannot flap, by arithmetic rather than a timer.** `shouldKill` pauses below the 52% ACOS pivot,
which is 1.923x. Revival needs 2.0x. The band between is dead space, and there is a test pinning it.

Both kills predated the ledger, so they were backfilled by keyword id. `phone tether` has 12 paused
copies and only one of them spent, which is precisely why the ledger keys on id and not text:

```
232082872464476  PHRASE  phone tether                    $7.55 -> $9.49    1.26x
101871591538849  BROAD   hand strap universal phone...   $13.61 -> $16.49  1.21x
```

Live: `revival: 2 killed this month, 0 back above 2.0x`. Correct.

## Rule 3 — the kill, pinned as a pure function

William: *"should not be pausing all key words when only 1 spends."*

Checked before answering. It was not, and here is the evidence rather than the claim:

- Five kills ever logged. 2026-08-08 `hand strap universal...`: 3 copies, only the BROAD one paused,
  EXACT and PHRASE still running.
- 2026-08-07 `phone tether` PHRASE shows 0 on / 6 off, which *looks* like a mass pause. The
  `kw_state_snapshot` for **08-05, two days before the kill**, shows five were already paused and
  only id 232082872464476 was enabled. That is the one the kill took.
- Account-wide, of 541 groups holding more than one copy, **281 are in mixed states**.

The concern was legitimate in origin: commit `78102eb "the $4 kill now pauses every copy"` is real.
I wrote it, wrote it up as though William had agreed, and he had not. It lives only on the PR #2
branch, was reverted inside that branch by `a9fc423`, and has never been on main.

Sponsored Brands and Display each had a test pinning per-copy behaviour. Sponsored Products did not,
so the guarantee rested on reading a loop. `killPlan()` is now pure and pinned by seven tests, the
sharpest being: **$3 + $3 across two copies is $6 and neither dies**, because neither reached $4 on
its own.
