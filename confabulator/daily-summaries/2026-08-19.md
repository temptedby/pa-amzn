## 3. THE LISTING FIELDS ARE OURS. THE 08-17 CONCLUSION WAS WRONG.

That day recorded that copy fields on Black, 2-Pack and Pro are catalogue-supplied and only the
3-Pack is ours. Wrong, and it would have stopped a week of Megan's work from ever shipping.

Probed per field on all four SKUs with VALIDATION_PREVIEW:

```
bullet_point         VALID on all 4
product_description  VALID on all 4
generic_keyword      VALID on all 4
item_name            content rule only, not ownership
```

Two traps produced the wrong answer. A GET returns those attributes as ABSENT, which means we never
supplied a value, not that we cannot. And a validation patch with an obviously fake title returns
`8541` "different from what's already in the Amazon catalog", which reads exactly like a permission
refusal. Submit a plausible title and the error changes to a content rule.

## 4. AMAZON HALVED THE TITLE ON 27 JULY, AND OUR TOOLING DID NOT KNOW

Titles are capped at **75 characters** in all categories except media since 2026-07-27, with a new
125-character Item Highlights field alongside, indexed equally for search.

```
our live titles      98-108 chars
Megan's drafts      167-176 chars
my morning rewrites 157-159 chars   <- also wrong
```

The Definitions API still reports `maxLength: 200` for our product type, and a 157-character title
validates as VALID. Both are behind the policy. Enforcement is not rejection at submission: Amazon
replaces over-long titles with AI-generated ones, giving brand owners 14 days to object.

**A second rule bites independently of length.** No word may appear more than twice, and
**"Phone Assured" spends one of the two allowances for "phone"**, so a title gets exactly one more
use. Error `100470` on all four drafts.

Megan then restructured tab 2 into Option A / Option B plus an Item Highlight each, and fixed the
length herself. Three of eight still failed, all Option A, all on the twice-per-word rule. One word
each fixes it. All eight now validate.

Published two artifacts for William: the 75-character cliff, and Megan's full copy with per-field
verdicts.

**Compatibility**, after a longer chase. William spotted the live page showing only "iPhone SE".
There are TWO fields and I had filled the wrong one:

```
compatible_phone_models            free text, 3 entries, 2200 chars   <- filled first, fine
compatible_cellular_phone_models   controlled vocabulary, 60 entries  <- the filterable one
```

The second rejected every human-readable name including "Apple iPhone 16", which was live on our own
listing, and "Apple iPhone 15 Pro", the schema's own example. A field rejecting its own stored value
means wire format differs from display format. It does: **snake_case tokens**, discovered by reading
our own ASINs through the Catalog Items API.

```
apple_iphone_16           renders as "Apple iPhone 16"
apple_iphone_se_1st_gen   renders as "iPhone SE"     <- the defect, on 2-Pack and 3-Pack
```

Final state, verified from the catalogue:

