# 2026-08-20 — The engine was never quiet, its logbook was

The morning review opened by repeating yesterday's headline, that the engine had stopped acting.
Checked against Amazon rather than against our own log, that was wrong. The engine has been pausing
keywords and moving bids the whole time. What died on 18 August was the record of it, and the reason
turned out to be a database loop nobody had looked at.

---

## 1. THE CORRECTION THAT REFRAMED THE DAY

`ad_engine_log` shows nothing for Sponsored Products since 08-18. Three other sources disagree:

```
                     ad_engine_log     kw_bid_history    live on Amazon
08-19 00:05             (nothing)            51
08-20 00:05             (nothing)            38          verified, upd 00:04Z
08-20 06:05             (nothing)             5          verified, upd 06:04Z
```

Seven of today's keywords pulled straight from the Ads API: every live bid MATCHES what the engine
recorded, all ENABLED, all stamped 00:04Z or 06:04Z.

**Root cause found in the code.** `kw_perf_snapshot` is written with one awaited INSERT per keyword,
327 sequential round trips to Turso, and it sits between the bid apply and `persistLog`. The run
dies inside that loop. The snapshot table shows the same wound from the inside:

```
08-19T06:04   315 rows written
08-20T00:05    75 rows          <- truncated mid-loop
08-20T06:05   122 rows
```

Everything after the loop is lost: the decision log, and `kw_kill_ledger`, which is the table the
in-month revival at 2.0x reads. **Kills recorded nowhere can never be revived.**

## 3. THE BID RULE CUTS WINNERS. WILLIAM CAUGHT IT.

He asked: if a term converts at 8x to 28x, should we not be raising bids to take the volume?

`ad-rules.ts:1171` says no. Every path after a keyword starts getting clicks is downward:

```
no impressions, no clicks    -> UP   $0.10
shown but never clicked      -> UP   $0.10
getting clicks, under 2x     -> DOWN $0.10
getting clicks, 2x or over   -> DOWN $0.02   "works, find the cheapest bid"
```

That is his own 08-10 instruction implemented literally. The size of what it governs:

```
12 keywords at 2x or better
  cost $29.02, returned $137.88  =  4.8x
  44% of all ad sales, on 5% of the spend
```

Against 305 keywords that have never converted and cost $351.74.

And a second gate stops the ROAS branches firing at all. `SEARCH_MIN_CLICKS = 3`, but most winners
get one click a month, so they never reach the test in either direction. Four of the twelve have not
been touched since 08-14. The ones that did climb, climbed on the no-clicks branch by accident.

## 7. WHAT SHIPPED

**14 keywords, live.** William approved PR #8's rule, so the harvest was applied through the REAL
`harvestCandidates()` rather than a hand-rolled copy.

```
POST /sp/keywords -> HTTP 207   success 14, error 0
read back from Amazon: 14 of 14 ENABLED at $0.50
```

It came to 14 rather than the 10 quoted, because the search-term report refreshed at 18:40 and picked
up two more converting terms. Nine distinct phrases, all 3.4x or better:

```
28.7x holdmate pro retractable phone holder   16.5x tourist phone safety cord
15.9x anti pickpocket phone                   12.3x phone assured retractable... (our own title)
11.2x lanyards for id badges                  11.2x stainless steel phone tether tab
 9.5x holdmate pro (second ad group)           8.5x anti pickpocket phone wrist strap
 3.4x retractable phone tether
```

Each rests on one order, so the evidence is thin per keyword. Worst case across all 14 is about $56,
because the $4 kill is the backstop.

**PR #11 — the engine every hour.** William: "We're supposed to be doing the engine every hour not
every six hours anymore."

```
report-warm   "0 */6"  ->  "0 * * * *"
ad-engine     "40 */6" ->  "40 * * * *"
```

The 40-minute lead stays, because the slowest report queue measured here is 31.5 minutes.
`cron-ordering.test.ts` was verified to FAIL against the six-hourly schedule before shipping.

Hourly is about the gap, not the count. A keyword went $0.75 to $4.72 between two runs on 08-18.
Fifteen kills have averaged $8.04 against a $4 bar. It does NOT mean bidding hourly: the 6-hour
per-keyword cooldown is untouched, so what runs 24 times a day is the kill check and the harvest,
and both are safer more often.

Also in #11: the snapshot loop batched, and `report-warm` no longer waits. Since PR #5 gave
`getReport` a 90-second inline wait, warm has been walking five specs at up to 90s each, a 450s worst
case against a 300s budget, where the last specs are silently never requested.

**PR #12 — the impressions bar.** 652 of the 674 raises since 08-14 came from one branch, on this
evidence:

```
min 0   p25 0   median 2   p75 11   p90 42   max 234 impressions
```

Account CTR is 0.595%, one click per 168 impressions. `NO_CLICK_MIN_IMPRESSIONS = 150`, which blocks
98% of them. A keyword with NO impressions still climbs, so the escape from the $0.10 floor trap is
untouched, and a held keyword keeps gathering impressions, so it is a delay and not a freeze.

427 tests pass on both, tsc clean.
